技术原理

只代理 TCP。底层用的 armon/go-socks5 只实现了 CONNECT，没有 UDP ASSOCIATE，所以覆盖范围是 TCP 连接 + 代理自己发起的 DNS 查询。客户端的 UDP 流量（QUIC、部分游戏）不会经过这里，会按系统默认路径走。

实例之间是真的隔离的。每个实例有自己的监听口、统计口径和拨号器，只共用一份台账文件 proxy.json。一个实例起不来（端口被占、绑的线路没生效）不会拖垮别的，也不会拖垮整个进程——启动日志里说明原因，该实例保持停止，后台照常进得去。

出口是在拨号时施加的。代理本身不决定走哪个网关，它只把绑定线路要求的记号打在出站 socket 上：Linux 是 SO_MARK，macOS 是源地址 + 线路专属端口段里的一个源端口，Windows 是 IP_UNICAST_IF。具体见「路由管理」页的技术原理。线路没生效时实例拒绝启动，不会退回默认网关——用户以为流量走了指定线路、实际还在默认出口上，是最难排查的一种故障。

代理 DNS 走同一条线路。客户端用 --socks5-hostname 时域名是交给代理解析的。那次查询同样带上本实例的出口记号（macOS 上 UDP 也单独有一条 PF 规则），否则查询会从默认网关漏出去，既泄漏了「这个实例在查什么」，拿到的解析结果也可能和数据连接的出口对不上。

统计怎么来的。每条连接被包一层计数器数字节；「目标地址」这一列则是借 go-socks5 的 RuleSet 钩子记下来的——只有那个位置能同时拿到客户端地址和请求目标。所以表里显示的是客户端请求的原始域名（带上实际解析到的 IP），而不只是一个 IP。

配置与运行状态是分开的。实例停着的时候也能改配置；开关状态跟着配置一起存盘，进程重启（升级、崩溃、机器重启）后照上次退出前的样子恢复，不用每次再来点一遍。

技术原理

这一页上是两件正交的事。下半部分的「自定义路由」按目的地选网关，下发到系统主路由表，全机生效；上半部分的「出口线路」按实例选网关。两者可以同时用。

为什么按实例选网关需要额外机制。路由查询的输入只有目的地址，所以光靠加路由，永远分不出「这个包是 8091 实例发的、那个是 8092 发的」——两个实例访问同一个目标时内核只有一条路由，必然走同一个网关。必须给包刻上一个记号，再让内核按记号选路。这个记号就是选择器。

Linux 的选择器是 fwmark。每条线路一个 mark、一张独立路由表、一条 ip rule：

ip route replace default via 192.168.1.254 dev eth0 src 192.168.1.5 table 7000
ip rule add priority 300 fwmark 0x40000000/0xff000000 table main suppress_prefixlength 0
ip rule add priority 301 fwmark 0x40000000/0xff000000 table 7000

编号是刻意挑的：路由表 7000–7063 避开内核保留的 0/253/254/255 与 mwan3 占用的 1–250；mark 用最高字节 0x40000000–0x7f000000，既有的使用者（mwan3、SQM、WireGuard、Tailscale）全挤在低三字节；优先级 300–427 排在 0: local 之后、mwan3(1001+) 与 main(32766) 之前。第二条规则里的 suppress_prefixlength 0 很关键：没有它，打了标的包完全不查主表，下面那张「自定义路由」表里的条目和 LAN 直连路由会统统失效；加上它之后主表只忽略默认路由、保留所有更具体的条目。ip 命令不支持该参数时会自动降级，并在能力横幅、这一页和启动日志三处都说明后果。

macOS 的选择器是源端口段。没有 fwmark，但 PF 能按五元组把包 route-to 到指定下一跳。每条线路分一段 256 个专属源端口（20000–36383，在系统临时端口段 49152 起之外），拨号时从段内选一个绑上，PF 里按「源 IP + 源端口段」匹配的规则把包送到该线路的网关。TCP 和 UDP 各一条规则——代理自己的 DNS 走 UDP:53，漏了它查询会从默认网关跑掉。规则写在 anchor com.apple/nettool 下，借系统 /etc/pf.conf 里现成的 anchor "com.apple/*" 生效，不用改你的 pf.conf；启动时会实际读一遍确认那行还在。

「验证」按钮问的是内核，不联网、不发一个字节。Linux 上是 ip route get <目标> mark 0x…，macOS 上是把 anchor 里此刻真正生效的规则读回来比对。这是唯一能区分同一网段两个网关的检查——两个网关同属一个 ISP 时，公网 IP 探测是分不出差别的。

自定义路由带台账。本程序下发的条目在 Linux 上打了 proto 210 标记，台账丢了也能靠 ip route show proto 210 认回来。填域名时会当场解析 A 记录、为每个 IPv4 下一条 /32 主机路由，之后每 5 分钟重解析一次：新增的补上、撤下的不再解析到的删掉；DNS 解析失败时保留现有路由不动，免得一次网络抖动把配置清空。

崩溃残留只能靠开机对账。内核里的路由和 ip rule 都没有「谁加的」这种信息，而进程被 kill -9 时拦不住也清不掉。所以退出时不做清理，改为启动时拿台账对一遍，把本程序装过、但台账里已经没有的孤儿规则和路由表清扫掉。macOS 不需要清扫：PF 的 anchor 是整份规则集一起加载的，下次启动重新加载时残留会被整份冲掉。

技术原理

四个平台的写入对象完全不同，所以这里统一成「目标 + 一组设置」：

  • macOS — networksetup，以「网络服务」为单位（一块网卡可能对应多个服务）
  • Linux — nmcli，以 NetworkManager 的「连接」为单位
  • OpenWrt — UCI，以 /etc/config/network 里的 interface 段（lan / wan / wwan）为单位；读用 ubus call network.interface dump，写用 uci set + commit + network reload。路由器上没有 NetworkManager，nmcli 那条路整个是断的
  • Windows — netsh，以接口名为单位

所以列表里的「配置对象」才是真正被写入的东西，en0/eth0/br-lan 这类设备名只用于展示和匹配。

读取一律不认本地化文案。Windows 的 netsh / route 输出跟着系统语言走（中文版打印的是「接口 xxx 的配置」「在链路上」），按文案解析在中文系统上必然错。所以那边的读取走 PowerShell 的 Get-Net*（属性名与枚举值固定），或者只认数据行的形状。

Wi-Fi 自动切换是轮询的。默认每 30 秒查一次当前 SSID（-wifi-watch 可调，0 表示关闭），发现换了网络就套用对应的配置档。没有启用任何配置档时只记录 SSID、不动配置。

改网卡配置需要管理员/root 权限，而且是立即写进系统的持久设置——不是本程序内部的转发规则，退出本程序也不会还原。切到 DHCP 再切回来是把它改回去的办法。

技术原理

一次查询的顺序：静态记录 → 缓存 → 上游。「来源」那一列显示的就是这次实际由谁回答的。

上游有四种形态。223.5.5.5 是普通 UDP（失败或被截断时自动改走 TCP）、tcp:// 强制 TCP、tls:// 是 DoT、https:// 是 DoH。TCP 与 DoT 在报文外面套 2 字节长度前缀，DoH 则是一次 HTTP 请求，每个 DoH 上游各自复用连接。

分流按域名规则最长匹配。给上游加了域名限制后，命中最长那条规则的上游来回答；一条规则都没命中时，退回到没写域名限制的兜底上游。这就是「境内域名走境内 DNS、境外域名走境外 DNS」的做法。

两种查询策略。「顺序」是按列表从上往下试，前一个失败才轮到下一个，所以上游的先后顺序有意义（列表里可以上下调）；「并发」是同时问所有上游、谁先回用谁，上游里混着境内境外时能省掉一次超时等待——不然慢的那个会把整次查询拖住。

缓存存的是入库那一刻的原始报文，取出来时按已经缓存了多久把 TTL 扣掉再返回，否则客户端会以为记录比实际更新。所以「最近查询」里同一个域名第二次的 TTL 会随时间递减。查不到记录的应答也会做短时负缓存。

DoT/DoH 上游是域名时需要 bootstrap。本机很可能正把这个 DNS 服务设成系统解析器，再走系统解析去查上游的域名就是自己问自己。配了 bootstrap 就用它先把上游域名解析成 IP。

改配置会重启查询引擎。一次启动对应一个引擎实例，换配置就整个换掉，处理中的查询不会看到改了一半的配置。

监听 53 端口需要 root/管理员，而且要先确认端口没被系统自带的解析器（systemd-resolved、dnsmasq、mDNSResponder）占着。想先验证可以用 -dns-port 5353 换个端口起。

Ping

走 ICMP echo。指定源 IP 就是从那块网卡发出去，用来验证"这条线路到底通不通"—— 同一个目标换不同源 IP 的结果，往往就是不同路由器的差别。 macOS 上普通用户也能 ping；Linux 非 root 时需要放开 net.ipv4.ping_group_range。

技术原理

ICMP 有两种套接字，权限要求不一样。非特权的 ICMP 数据报套接字（macOS 默认就能用；Linux 要求当前用户的 gid 落在 net.ipv4.ping_group_range 内）和需要 root 的原始套接字。ping 优先用前者，好让非 root 也能用。Windows 压根没有非特权 ICMP 套接字，只剩原始套接字这一条路，所以那边必须以管理员身份运行，另外防火墙要放行 ICMP 入站。

「指定源 IP」是这里最有用的开关。它把 ICMP 套接字绑到本机某个地址上，于是回包走的是那条链路。同一个目标换个源 IP 再试一次，哪条线路通、哪条不通就一目了然——这也是排查出口线路时的第一步。

发包节奏。按设定的间隔一包一包发，每包等到回包或超时为止，结果一条条追加，页面轮询时边跑边看。次数填 0 是「一直 ping」；页面关掉之后没人来停它，所以内部兜了一个总时长上限，到点自动停。

超时不等于不通。不少主机和防火墙默认丢弃 ICMP echo，TCP 却是通的。那种情况下 ping 不通不说明问题，改用「实际出口公网 IP」检测或直接 curl 更可靠。

路由追踪 (Traceroute)

逐跳加大 TTL，让沿途每个路由器各回一个超时报文，从而把整条路径问出来。 第一跳通常就是这个源 IP 对应的路由器，很适合确认"流量是不是真的走了那条线"。 Linux 上需要 root：非特权 ICMP 套接字收不到中间路由器的回包，那样整趟都会是超时。 中间设备不回 ICMP 时显示 *，属正常现象；连续 5 跳无回应会提前结束。

技术原理

靠 TTL 把路径问出来。TTL 从 1 开始一跳一跳往上加：TTL 用完的那台路由器会回一个 Time Exceeded，从而暴露自己的地址；哪一跳收到的是目标回的 Echo Reply，就说明到了。

这里必须用 root。与 ping 相反，traceroute 优先用原始套接字——非特权的 ICMP 数据报套接字在 Linux 上收不到中间路由器回的 Time Exceeded，那样整趟都会是超时。Windows 上同样需要管理员身份；那个平台还读不到回包的 TTL（底层库没实现对应的控制消息），所以 TTL 那一列会显示 0。

星号不代表断了。很多路由器出于策略不回 ICMP，或者对 ICMP 限速，中间几跳超时是常态。只要后面的跳还有回应、最终到达了目标，路径就是通的。

「指定源 IP」决定这趟从哪条线路出去。多网卡/多网关的机器上，不指定就是走系统默认路径。想确认某条出口线路实际经过哪些路由器，就把源 IP 填成那条线路的本机地址。
